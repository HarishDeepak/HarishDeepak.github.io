Fine-tuning a diffusion policy, and reporting that it didn't help

A pretrained 251.8M-parameter visuomotor diffusion policy from LeRobot, run closed-loop on PushT. It sees a camera image and the end-effector position and outputs the next target, the same interface real manipulation policies use. Most of the work turned out to be finding two bugs that fail silently.

Model
LeRobot Diffusion Policy
Task
PushT (gym_pusht)
Method
LoRA rank 8, peft
Code
repo

Bug 1: right shape, wrong by orders of magnitude

The published checkpoint stores its normalization statistics in submodules the current LeRobot release no longer defines. Loading it prints one warning, drops the statistics and keeps running, so the actions look plausible and are numerically wrong. The fix reads the statistics straight from the safetensors file and applies them by hand, following the checkpoint's own config.

Bug 2: more than 100 GB of RAM

With a shuffled DataLoader on the video-backed dataset, every sample seeks into a different video file, and PyAV's decoder resources pile up instead of being freed. Sequential loading avoided the leak but left the loss flat. Decoding all frames into memory once, then shuffling tensors, fixed both.

What didn't work

The success rate didn't move. Three seeds flipped from fail to success and two the other way. The base model had already seen all 206 PushT episodes, so a 60-episode subset of the same data had little to add.

What the project does show: adapters on exactly the intended FiLM layers, a loss that goes down once the data pipeline is fixed, and a clean save, merge and reload. The obvious next test is fine-tuning on data aimed at the seeds that still fail.
